# Region Builder: AWS Certified Solutions Architect – Associate (SAA-C03)

A game-style study app. The player is the chief architect building a city inside an AWS Region, spread across three islands (Availability Zones). It is built in steps; **each step ends with an audit that the owner reviews. Do not start the next step until they approve.**

## Stack
Vite + React 19 + TypeScript (`strict`, `noUncheckedIndexedAccess`) + Tailwind v4. No backend; progress is saved in `localStorage` under a **versioned save schema with migrations** (`src/save/`). Vitest for unit and DOM tests, ESLint flat config, Playwright (Chromium) for the layout test. Hash routing (`#/map`, `#/atlas`, `#/<view>/<buildingId>`, plus `#/review`, `#/weak`, `#/mock`) so static hosting needs no rewrite rules.

## Lessons from previous study apps (apply from the start)
1. **Shuffle every question format at render time** and keep source files balanced (answer positions, multiple-response positions). Use `shuffle()` from `src/lib/rng.ts`.
2. **Debug and test hooks (such as `?seed=`) work only in dev builds**, behind `import.meta.env.DEV`; `check:bundle` proves they are absent from production (it fails if a dev build is checked).
3. **React effects always use block bodies.** A one-line `useEffect(() => scrollTo())` returned scrollTo()'s Promise and crashed a page on current Chrome. The `no-restricted-syntax` rule in `eslint.config.js` rejects expression-bodied `useEffect`/`useLayoutEffect`/`useInsertionEffect`; `src/lintRule.test.ts` proves it fires.
4. **Self-hosted fonts and no external origins** (strict CSP meta in production, offline PWA later). No inline `style=` attributes. **Code-split by feature** (`React.lazy`).
5. **Every fact cites an allowed source.** Keep the needs-verification queue; use `BANNED_TERMS` (`scripts/banned-terms.ts`) for disputed claims; show contradictions between docs both ways (`content/contradictions.json`) while keeping them out of questions.
6. **Content is reviewed by separate reviewer agents**: a blind pass, then a source pass.

## The game
- **Districts = exam domains:** Citadel (Secure), Harbor & Levees (Resilient), Express Quarter (High-Performing), Treasury (Cost-Optimized). Founders' Square holds the Foundations. Islands A/B/C are the three AZs; placement is cosmetic.
- **Buildings** group 2–5 outline bullets from one task statement; every bullet belongs to exactly one building. At most 5 **Foundations** cover background the outline assumes but no bullet teaches.
- **States:** planned (locked) · surveyed (idle) · under construction (running) · commissioned (certified). Only the last two are stored; planned/surveyed are derived from prerequisite roads.
- **Roads** are prerequisites with a one-line reason. Rules (tested): acyclic, every building reachable from a start building, no road implied by other roads.
- **Service families:** Security & Identity, Networking & Content Delivery, Compute, Storage, Database, Application Integration, Analytics, Management & Governance, Migration. The Service Atlas groups buildings by family; links across districts are computed from shared families. Deviation: Cost Management, Containers, Serverless and Developer Tools fold into the closest family (`src/data/families.ts`); Machine Learning has no family.
- **Carryover tags:** *portfolio* (S3 static hosting, CloudFront, Lambda, API Gateway, DynamoDB; later steps add a placement check on SAA-level design decisions, never definitions) and *Azure crosswalk* (concept pairs from the Microsoft Learn comparison pages; Step 2 adds the short note, including where the analogy breaks).

## Naming rule (renamed services)
Questions use the service names from the exam guide's in-scope list and the short-names list (`scripts/official-short-names.json`, diffed by `check:content -- --live`). Notes show the current name beside any rename, written `{{rename:id}}`, with sources for both names. `content/renamed-services.ts` holds each verified rename (IAM Identity Center, SageMaker AI, Amazon Quick, Amazon Data Firehose). A note that uses an old or other name outside that list fails `check:content`.

## Notes model (Step 2)
Notes for every building live in `content/notes/<district>/<building>.ts` (lazy chunk per district through `src/content/district-*.ts`). A note is built from blocks `b(text, sourceIds, quotes, opts)`: every block cites pages from `content/sources.ts` and carries verbatim quotes that `check:links` verifies against the live page. Checks (`check:content`): a number or number-word in prose must appear in a quote of the same block; no prices; deprecated/retired/preview words need a `status` label and a quote that says so; old service names need `{{rename:id}}`; Microsoft Learn sources only inside "Coming from Azure" blocks (each needs an AWS source too); each glossary term is defined once (`content/glossary.ts`) and used; no unused source; the required "don't confuse" pairs exist (`content/dont-confuse.ts`, list in `scripts/lib/notesChecks.ts`); `scripts/banned-terms.ts` blocks disputed claims. Where two pages disagree, both readings go in `content/contradictions.json`; what cannot be confirmed goes in `content/needs-verification.json` and is kept out of the notes. In the UI, "In a design" blocks and scenario cues are labelled study guidance, not AWS statements.

## Exam-era rule (services whose status changed)
If a service is on the exam guide's in-scope list and AWS docs still describe the capability, it may be a correct answer, and the explanation must state its current availability with a source (for example "closed to new customers"). Never write a question whose answer depends on the availability status itself. Services not on the in-scope list (App Runner, Timestream, Elastic Disaster Recovery) are never answers and never appear in a stem or option; notes may name them as context only. `content/exam-era.json` records each case with its AWS sentence and source id. Status labels (`preview`, `deprecated`, `retired`, `closed`) sit on the specific claim, never on a block whose main point is current.

## Question bank (Step 3)
Questions live in `content/questions/<district>/<building>.ts`, built with `mc()` and `mr()` from `content/questions/helpers.ts` (multiple choice: 1 correct of 4; multiple response: 2 or 3 correct of 5 or more; about 80/20). Each question has a building, outline bullets (none for Foundations), difficulty 1 to 3, tags (`placement-eligible`, `mock-reserve`, `trap:<pair-id>`), an explanation for every option, and verbatim AWS-page `evidence` quotes that `check:links` verifies. Options are stored in an authored order that the checks keep balanced and are shuffled at render time (`src/questions/present.ts`). The writer rules are in `docs/question-writing-guide.md`; per-building targets in `docs/question-plan.json`; review logs in `docs/reviews/`.
- **Size and weighting:** at least 3 live questions per bullet and 8 per building; domain shares within 2 points of 30/26/24/20 (Foundations excluded); difficulty about 20/55/25 with level 3 at 22% or more; at least 8 `placement-eligible` questions on every portfolio building (design decisions beyond the projects, never definitions).
- **Mock reserve:** questions tagged `mock-reserve` are never reachable by any draw except the `mock` mode in `src/questions/pool.ts`. Only `src/questions/*` may import question data (ESLint rule plus a scan in `check:content`); `check:bundle` proves the question data and the tag are absent from the entry chunk.
- **Answer-key access:** there is no route. The browser opens only from Settings behind a warning, holds its state in memory and never lists the reserve.
- **Question rules (checked):** in-scope service names only (also not Service Quotas, Application Auto Scaling or any out-of-scope name); no availability wording in a stem or option; no "all/none of the above"; no open needs-verification item or banned term; exam-era services carry `era` and the availability source; answer positions balanced (no position over 35% of MC, 60% of MR; correct option strictly longest in at most 40%); no near-duplicate stems (checked bank-wide).
- **Review per district:** writers, then a blind pass (`scripts/export-blind.ts`, `scripts/score-blind.ts`), then a source pass; every dispute is fixed or replaced and logged in `docs/reviews/<district>.md`. Helpers: `scripts/check-building.ts`, `scripts/rebalance-slots.ts`, `scripts/questions-stats.ts`.

## Post-guide rule (features newer than the exam guide)
The exam guide dates from August 2022. A feature AWS introduced on or after **2022-08-01** is *post-guide*. `content/post-guide.json` is the registry (id, name, introduced, certainty, source + verbatim date quote, `patterns`, `predecessorPatterns`; `preGuide` records candidates that turned out older). Rules, enforced by `check:content`:
- A question whose text (stem, options, explanations) matches a registry feature must declare it in `postGuide` (adds the `post-guide` tag). Every note block that matches carries `newer: [...]`, shown as a "Newer than the exam guide" label.
- **A post-guide feature may never be the key when the established design is a wrong option.** A question with `postGuideKey` fails if any option matches that feature's `predecessorPatterns` (for example DataSync Enhanced mode must not beat a Basic mode task with an on-premises agent; regional NAT must not beat one NAT gateway per Availability Zone). Rewrite to test the exam-era design, or compare the newer feature only with options that are wrong for other documented reasons.
- `post-guide` and `mock-reserve` never go together, and `mock` draws exclude `post-guide` (`src/questions/pool.ts`).
- Use `scripts/post-guide-scan.ts` to list matches, `scripts/post-guide-tag.ts` / `post-guide-label.ts` to add declarations. Dates come from AWS What's New / documentation history pages; anything undatable is treated as post-guide.

## Game loop (Step 4)
- **Lifecycle:** planned (a prerequisite is not commissioned) → surveyed (derived) → under construction after opening the building's notes and passing a 2-question start-up check (both right; new draw on retry, no daily limit) → commissioned by a 5-question inspection at 4/5 or better. A second failed inspection of one building on one local day locks its inspections until the next local day; leaving an unfinished inspection counts as a failure. Draws use the building's live questions only (never `mock-reserve`), cover each bullet where possible, include one at difficulty 2 or 3 and avoid the previous attempt's questions.
- **Placement** (19 portfolio buildings only, even while planned): 5 `placement-eligible` live questions, all 5 right; one attempt started per building per local day (counted at start; a reload resumes it). Passing commissions with a visible "Placed" mark and unlocks dependents.
- **Scoring: full credit only.** A multiple-response question is correct only if exactly the keyed set is chosen. The key is shown only after the attempt is finished.
- **Local day** = the calendar date in the browser's time zone (`Intl.DateTimeFormat`); day arithmetic uses calendar components, so 23/25-hour days (for example 1 Nov 2026) behave like any other day.
- **XP:** a correct answer earns 10 / 20 / 40 by difficulty 1 / 2 / 3, any later answer to the same question a quarter (3 / 5 / 10); +50 once per building on commissioning. **Ranks:** Surveyor 0 · Apprentice 150 · Foreman 500 · Mason 1,200 · Builder 2,500 · Architect 4,500 · Master Builder 7,000 · City Planner 10,000 · Chief Architect 13,000. **Streak:** a local day counts at 10 answered questions. **Badges:** four districts, Foundations, all portfolio buildings, a flawless (5/5) inspection, 7- and 30-day streaks, whole city.
- **Readiness** per domain = accuracy over the last **30** counted answers × bullet coverage (share of the domain's bullets answered correctly within the last **100** counted answers), "—" below **10** counted answers; overall weights 30/26/24/20 and is "—" until all four domains have a value. Counted: inspection, placement (later review, puzzle, lab, mock). Start-up checks never count.
- **Save v2:** `game` block (notes opened, attempts in progress, XP, seen counts, days, badges, flags, compact answer log capped at 4,000); migration chain in `src/save/migrate.ts`. Flags are local, listed in Settings and exportable as text.
- Engine in `src/game/` (pure functions over the save, injectable clock and city); UI in `src/ui/play/` and `src/ui/ProgressPage.tsx`.

## Puzzles (Step 5)
- Seven types: Policy Court (IAM evaluation), Packet Tracer (VPC traffic), Disaster Bunker drill, Cold Cellar planner (S3 lifecycle), Purchase Planner (compute pricing models), Architecture Builder, Qualifier Sprint (Town Charter). Contract in `src/puzzles/types.ts`; evaluators in `src/puzzles/<type>/def.ts`; scenarios (inputs only) in `content/puzzles/<type>.ts`; writer rules in `docs/puzzle-writing-guide.md`. Puzzle ids are `puzzle-<type>-NNN` (the prefix keeps them apart from question ids such as `cold-cellar-001`).
- **Computed answers:** where rules decide, a small evaluator applies rules that each carry an AWS quote (`Rule.src` + verbatim `quote`, verified by `check:links`); the answer is computed, never stored. An evaluator returns `null` (a refusal) for anything its rules do not settle, and `check:content` rejects any scenario that hits one. Architecture Builder and Qualifier Sprint are authored with sourced checks/facts.
- **Practice only:** a puzzle play earns XP like a question (10/20/40, repeats a quarter), counts toward the streak, is logged with attempt type `puzzle` and feeds readiness, but never changes a building state. **In each domain's 30-answer readiness window at most the 8 most recent puzzle plays count** (older ones are skipped); a domain still needs 10 counted answers, so puzzles alone never produce a readiness value. Town Charter (a Foundation) has no domain, so its plays never affect readiness.
- **Workbench:** each building's panel lists its puzzles once the building is surveyed (any state except planned). Routes `#/workbench/<building>` and `#/puzzle/<id>`.
- **Rules:** no puzzle text or rule may match a post-guide registry feature (a rule that must may declare `newer`, and no scenario's answer may depend on it); in-scope services only; banned terms and open queue items apply; reviewed by a blind pass and a source pass (`docs/reviews/puzzles.md`).

## AWS Free Tier facts (Step 6; recorded from AWS pages, re-check before relying on them)
Sources: AWS Billing guide "Choosing a plan" (`docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier-plans.html`), the Free Tier FAQ (`aws.amazon.com/free/free-tier-faqs/`) and `aws.amazon.com/free/`.
- **Two plans.** New accounts choose a **Free plan** or a **Paid plan**. Both receive sign-up credits and can earn more by completing activities (the amounts are on the Billing page; labs never quote money). Both include "Always free" offers. The Paid plan adds short-term trials and access to all services; charges beyond the credit balance are pay-as-you-go. A Paid plan cannot be downgraded to the Free plan. (Free Tier FAQ: "No, you cannot downgrade your Paid plan to the Free plan.", source id `free-tier-faq`, verified by `check:links`.)
- **Free plan.** "Ensures you won't incur any charges." It ends after **six months or when the credits are fully used, whichever comes first**. Then the **account closes automatically**; AWS retains content for **90 days** before permanently deleting it, and the owner can upgrade to the Paid plan within those 90 days (remaining credits then apply to later bills). The plan cannot be extended beyond 6 months. Credits are not transferable and the Free plan is not eligible for other promotional credits.
- **Limited to select services.** "Free account plans don't include access to AWS services and features that could possibly deplete your credits" (examples named: Savings Plans, Reserved Instances, certain Marketplace offers). The list of eligible services is on `aws.amazon.com/free/`; the FAQ has no list of its own. A lab's plan badge is therefore **Free plan compatible** only where that page was checked, **Paid plan only** where a documented rule excludes it, and **availability not confirmed** otherwise.
- **Automatic upgrade to Paid.** A Free-plan account upgrades itself if it joins AWS Organizations, sets up an AWS Control Tower landing zone, joins the AWS Partner Network, creates a Professional Services contract, enrols in an Enterprise Agreement, buys an AWS Skill Builder Team subscription, or is designated HIPAA or SEC compliant. So the Organizations lab is Paid plan only.
- **Credit expiry is stated two ways** (6 months in one FAQ answer, 12 months in another): `content/contradictions.json` (`c-free-credit-expiry`). Plan on 6 months for a Free-plan account and read the real date and balance in the Billing and Cost Management console.
- **Recommendation:** use a **dedicated lab account**, separate from the portfolio account, so lab cleanup mistakes, the 6-month closure and Organizations upgrades never touch the portfolio.

## Spaced review, maintenance and Weak Spots (Step 7, save v5)
- **Schedule (from `game.history` only, never the capped log; `src/game/review.ts`).** A question's next review day is the local day of its last answer plus an interval: **a miss comes back the next day; a correct run of 1, 2, 3, 4, 5, 6 answers earns 1, 2, 4, 7, 14, 30 days, and 30 for every longer run.** Eligible: answered, live and in the loaded bank. **`mock-reserve` questions are never reviewed**; puzzle ids are not reviewed.
- **Daily Review (`#/review`).** Due questions first (most overdue, then the lower run), at most **25 review answers per local day** (`game.reviewDay`); when fewer are due, the rest is topped up from the **weakest bullets** (`game.byBullet` accuracy ascending; one question per bullet per pass, least-seen first, never what was answered today). A session is `game.review` (resumes on reload; leaving costs nothing). Review answers are logged as kind `review`: they count in readiness, earn XP with the repeat rule, count for the streak, and never change a building.
- **Maintenance.** A commissioned building shows **"Needs maintenance"** on the map card and in its panel when its last 8 review and mock results (`game.maint`) include **at least 5** and **fewer than 60%** are right. The mark is derived (it clears when accuracy recovers) and never removes commissioning. The 5-question set (`#/maintenance/<building>`) takes the building's live questions, recent misses first, then the least accurate, then the least seen.
- **Weak Spots (`#/weak`).** Bullets ranked by the last 10 counted answers (`game.byBullet`), each with its number of answers ("not enough data" under 3; weak is under 70%); don't-confuse pairs by misses (`game.traps`); service families pooled over their buildings' bullets (weak at under 70% over at least 10 answers, also marked on the Service Atlas); flagged questions; links per bullet to its notes, a puzzle, the Workbench and a lab. `byBullet` is backfilled once from `recent` for saves made before version 5.
- Save v5 also holds `game.mock`, `game.review`, `game.statsBackfilled` and `labs.progress[id].ack`; `MIGRATIONS[4]` is tested on a real v4 save (`src/save/__fixtures__/save-v4-real.json`). The review draw lives in `src/game/reviewDraw.ts` and the mock draw in `src/game/mockDraw.ts`, lazy chunks because they name the reserve tag.

## Mock exam (Step 7)
- **Format** (exam guide and certification page, see "Exam facts"): 65 questions in 130 minutes, multiple choice and multiple response only, weighted 30/26/24/20 exactly by largest remainder (**19 / 17 / 16 / 13**). All 65 are scored in the mock; the UI says the real exam has 15 unidentified unscored questions. No feedback until the end; unanswered counts wrong; full credit only.
- **Draw (`src/game/mockDraw.ts`).** Never post-guide (the pool's `mock` mode), never a Foundation. Within a domain: **reserve questions nobody has answered come first**, then live questions; both phases avoid the last mock's questions, prefer ones not answered in the last 14 days, then the least seen, and spread round-robin over the domain's bullets. A domain short of reserve is completed with live questions (weights stay exact). On the real bank (130 reserve: 39/34/31/26): mock 1 uses 65 reserve, mock 2 uses 64 (domain 3 has 31 reserve for 16+16 slots), mock 3 takes the 1 left plus 64 live.
- **Clock.** `game.mock.active` stores the start time; the remaining time is computed from it, so it survives reloads, and a mock that expired while the app was closed is graded and submitted on load (`MockGuard`). Answers are saved as you go; the review screen lists all questions with jump links.
- **Results.** Raw percent overall and by domain, per-bullet results weakest first, every question with key, explanations and sources, the trap pairs fallen for, the history of the last 30 mocks, and the plain note that **720 is a scaled score and scoring is compensatory, so a raw percentage cannot predict it exactly.** Mock answers count in readiness (kind `mock`), earn XP, feed `byBullet`, `traps` and `maint`, and never commission.
- **Freshness.** A mock **counts** only if at least **50%** of its questions were not answered in the **14 calendar days** before it started (an answer on a day up to 14 days before the start day is "recent"). The fresh count and the verdict are fixed at the start, stored, shown, and explained in the UI when a mock does not count. Short dev mocks never count.
- **Ready to book.** Shown when the **two most recent counting mocks** each score **at least 80% overall with every domain at least 70%**. It is a study signal, not a prediction. The panel points to AWS's own checks, which the certification page names: the **Official Practice Question Set** ("to understand exam-style questions") and the **Official Practice Exam** ("assess your exam readiness"), linked through `aws.amazon.com/certification/certified-solutions-architect-associate/`.
- **Dev-only short mock:** `?mock=short` (10 questions, same pipeline) behind `import.meta.env.DEV` in `src/dev/mockShort.ts`; `check:bundle` fails if its marker is in `dist/`. `e2e/mock.spec.ts` runs it against the Vite dev server (a second Playwright web server), everything else against the production preview.

## Fact-check rules (Step 8)
- **Verdicts** (checker and spot-check): `confirmed`, `wrong`, `unsupported`, `outdated`, `source-changed`. Each non-confirmed verdict carries a `fix`. Ledgers: `docs/reviews/step-8/ledger/*.jsonl`. Spot-check samples and verdicts live under `.cache/audit/spot` and the scratchpad, not in the repo.
- **Adjudication categories** for an overturned claim: (a) answer key wrong, (b) claim false or outdated, (c) claim true but the quote does not state it directly (inference, missing qualifier, paraphrase beyond the page), (d) already fixed in the current text.
- **Gate:** only (a) and (b) count as errors against the 3% limit of the 172-claim spot-check sample (5 or fewer passes). Every (c) is fixed anyway, by rewording to what the page says or adding a verbatim quote that states it. If (a)+(b) is over 3%, re-audit only the groups where they occurred, then report before continuing.
- **Supported standard:** the quote states the claim, or the claim follows from it with no outside facts. Illustrative examples (for example the documentation range 203.0.113.0/24) are allowed when labelled illustrative. A distractor explanation needs support only for the factual reason it gives.
- **Freshness:** `content/page-hashes.json` stores a hash of each cited page's main content at verification time. `npm run check:freshness` (network) reports changed pages and the buildings, questions, puzzles and labs that cite them. It is not part of `npm test`, `check` or `check:all`. Refresh with `npm run check:freshness -- --update` only after the content is final.
- **verifiedAt:** each source carries the date it was last verified by `check:links` or an audit. A building shows the oldest date among the sources it cites ("Last checked on AWS docs").
- **Disagreements:** where AWS pages disagree, both readings go in `content/contradictions.json` and a disagreements block in the note. Disputed wording stays out of questions.
