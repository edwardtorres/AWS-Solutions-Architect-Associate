If lab-04-vpc fails to delete, the VPC, and with the NAT stack the NAT gateway and Elastic IP, remain. -> add to the verify list `aws cloudformation list-stacks --stack-status-filter DELETE_FAILED CREATE_COMPLETE --query "StackSummaries[?starts_with(StackName,'lab-04')].StackName"` and a sentence on retrying delete.

[low] step routes: the checkpoint "private route tables do not [have an internet route]" is only true before the optional NAT stack is created; order is right (routes before nat-stack) but the owner may revisit. -> add "before you create the NAT stack".
[low] template/capabilities: no IAM resources, so no CAPABILITY flag is needed. Fine. Both templates parse as plain resources; SG description uses only allowed characters.

## lab-05-s3-security-storage

[medium] steps cmk/c-key and cost `cmk`: c-key says the key "keeps billing until it is deleted", but the AWS KMS pricing page says there is no charge for a customer managed key scheduled for deletion. -> correct the wording (billing stops when deletion is scheduled; the key stays visible for 7 to 30 days), cite the pricing page, and tell the owner to pick the 7-day waiting period.
[medium] step lifecycle: "Use the day values the console accepts" is vague and the quote only says lifecycle can be set through the console or CLI. The transition page says objects smaller than 128 KB do not transition by default, so the lab's small text objects will never show the rule acting; the minimum days before an infrequent-access transition is also not given. -> give the exact values the page allows (and quote the 128 KB and minimum-days sentences), or state that this step only creates the rule.
[medium] steps kms-default, cmk, c-key: the KMS key pages show key ARNs containing the account number; none of the three is `sensitive: true`. v-key output (state only) is fine. -> mark them sensitive.
[low] step v-bucket (and every CloudShell command using $BUCKET): the variable is lost if CloudShell restarts or times out, and `head-bucket "$BUCKET"` would then run with an empty value. -> add "set BUCKET again if the shell was restarted".
[low] step public-policy: if the policy is unexpectedly accepted (Block Public Access was changed), the bucket would be public with an object in it. -> add "if it succeeds, delete the policy and re-enable Block Public Access at once".
[low] step c-empty: the claim that the CLI force option leaves versions behind is not on the cited page. The page also advises removing incomplete multipart uploads (their parts bill), which is not mentioned, though the lab creates none. -> drop the CLI claim or source it; add the multipart sentence.
[low] cost: calls made with the AWS managed key and the customer managed key are charged per request (pricing page); not a badge-worthy resource but "S3 versions" and KMS requests could be named in the goal. Storage left in a versioned bucket is covered by c-empty and bucket delete (a bucket with versions cannot be deleted, so v-bucket really proves cleanup).
[low] verify v-key: once the key is scheduled the alias stays, so the command prints PendingDeletion for the whole waiting period; correct, and described. If the owner skipped the key the call errors as described.
[low] plan: S3 and KMS read as free, CloudShell unconfirmed -> "not confirmed". If CloudShell were confirmed the derived badge would become "Free plan compatible" despite the optional customer managed key, which does not suit the Free plan. -> same rule as lab 04.
[low] step tls-policy: quote supports the SecureTransport recommendation; the CLI JSON is correct (escaping works inside a double-quoted shell string, `$BUCKET` expands).
Cleanup/leftovers: after c-empty, c-bucket, c-key and the verify steps nothing billable should remain; the key is the only item that can outlive the bucket and it is covered. Lifecycle rule, policy and encryption settings go with the bucket.
Privacy: bucket name appears on screen; no account IDs in commands; the bucket policy ARNs use the bucket name only.

## Summary

Labs 01, 02, 04 and 05 are well structured and mostly sound, with accurate cleanup and verification commands. The most serious defect is in lab 03: the member account is created in the organization root and never moved into the OU that carries the SCP, so the core demonstration (the deny) will not work, and the default SCP and SCP enablement that the console performs are not accounted for. Lab 03 also under-states that the Free-to-Paid upgrade cannot be undone by deleting the organization, which affects the plan assumptions of the later labs. Other recurring problems: `needs` omits the administrator user from lab 01 (labs 02 and 03), CloudShell is used but not listed in `services` (labs 01 to 03), KMS key ARNs and role pages are missing `sensitive` flags, a few steps go beyond their quotes (lab 05 lifecycle and KMS billing wording, lab 04 EIP release), and the CloudFormation cleanup has no DELETE_FAILED check.
