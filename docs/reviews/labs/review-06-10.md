## lab-06-cloudfront-oac

[medium] step distribution: the cited page (cf-get-started) shows the wizard also has an "Enable security protections" page that offers AWS WAF protections, which bill; the lab never says to decline them and `costs` has no WAF entry -> add "Do not enable AWS WAF protections" to the step (or add an optional WAF cost entry with a source and an alt).
[medium] step bucket-policy: the same page says that when the wizard creates the distribution "CloudFront updates the S3 bucket policy for you", so the manual paste step may duplicate or overwrite the policy the wizard already wrote; the claim that "the distribution settings offer a copy of the policy" is not in the cited quote (cf-oac quote only covers the principle) -> say: open the bucket policy first; if it already names cloudfront.amazonaws.com and your distribution, skip the paste; otherwise copy the policy from the distribution's origin settings (cite the page that shows that button).
[medium] step v-bucket: `$BUCKET` is a CloudShell shell variable set in step `bucket`; CloudShell sessions end after inactivity and the variable is lost, then `head-bucket --bucket ""` fails with a validation error, not "Not Found", so the verify can look like a pass -> have the owner re-set BUCKET first (put `BUCKET=<your-bucket-name>` at the start of the code) or use `aws s3api list-buckets --query "Buckets[].Name"` and compare by eye. Same for `$BUCKET` in `direct-before` and `direct-after`.
[low] step distribution: "default root object index.html" and the label "Sign requests (recommended)" are not covered by the quote (quote only says OAC sends authenticated requests); the page says the wizard picks recommended settings by itself -> cite the default-root-object page or drop the instruction; keep the OAC label tied to cf-oac.
[low] step upload: quote is about opening the CloudFront URL, not about uploading to S3 -> cite an S3 upload page (quote about uploading objects).
[low] step distribution: the console distribution page shows the distribution ARN (contains the account ID) and the bucket policy step is the only sensitive step -> set `sensitive: true` on `distribution` as well.
[low] step c-dist and verify: the OAC object stays after the distribution is deleted (free, but a leftover), and if the owner validated the certificate with a Route 53 hosted zone that zone bills; neither is in `costs`, the cleanup or the verify -> add a cleanup line for the OAC and for any hosted zone or validation record created for the optional ACM step; add `aws acm list-certificates --region us-east-1 --query "CertificateSummaryList[].DomainName"` to the verify steps.
[low] step v-dist: with no distributions `--output text` prints `None`, not an empty line, so the checkpoint "output is empty" is slightly wrong -> "The output is empty or says None".
[low] step distribution: I could not confirm whether the current wizard asks for a CloudFront pricing plan before creating; the lab and `costs: []` are silent -> check the live wizard once; if a plan choice exists add a sentence telling the owner which option has no monthly fee, with a source.
[low] trap cloudfront-vs-global-accelerator: quote proves Global Accelerator gives static IPs but not the sentence "would not cache it" -> cite a page that states Global Accelerator does not cache, or soften the text.
[low] step acm: ACM must be in us-east-1 while the lab says "stay in your chosen Region"; the step explains it but CloudShell commands in other steps use the chosen Region -> add "return to your chosen Region afterwards".
Checked and fine: step order (bucket, object, distribution, policy, test, cleanup distribution before bucket matches cf-oac); no versioning so `c-bucket` leaves nothing; no prices; no account IDs; plan badge derives to "not confirmed" (CloudShell, ACM unknown) which is honest.

## lab-08-dynamodb-design

[medium] step s7: the checkpoint says the Scan "capacity used is higher than for the Query". With eight items of about 100 bytes, both calls round up to one 4 KB read unit, so both report the same ConsumedCapacity (eventually consistent: the same half unit). [medium] step s12 / costs: point-in-time recovery is a billed feature (continuous backup storage) but has no `costs` entry and s12/c2 do not reference one -> add a `pitr` cost with the billing basis quote from the pricing page, list it on s12 and c2.

[medium] step s8: a GSI on `Status`, which has two values, is a hot-partition anti-pattern; the lab presents it as the correct design for "OPEN orders" -> add a one-line caveat with a source (choose a high-cardinality partition key, or add a sort key such as order date) so the owner does not learn it as a pattern.
[low] step s12: text says "read the restore window" but the query prints only the status -> add `EarliestRestorableDateTime` to the query or change the text.
[low] step s9: describe-table and the index query are in one code block; if the index is still CREATING the query fails -> split into two commands or add a `until` loop.
[low] verify v1: system backups made when a PITR table is deleted are not looked for -> add `aws dynamodb list-backups --backup-type ALL --query "BackupSummaries[].TableName"`; the checkpoint should then say system backups of LabOrders may show and are free for up to the page's period.
[low] step c2: the source is the pricing page, used for a retention behaviour (the guide allows pricing pages for billing basis only) -> cite the DynamoDB backup/PITR documentation page that states system backups on delete.
[low] needs: `lab-01-safe-account` is not actually used by any step (no result carried over) -> remove or explain (budget guard).
Checked and fine: composite key, update-table GSI on a pay-per-request table needs no throughput, TTL attribute name and format, JMESPath in v1 quotes correctly, step order (index before TTL before PITR before cleanup), prov table cleaned in c1, no prices, plan badge "not confirmed" (CloudShell unknown) is honest.

[high] steps c-stack/v-db: there is no wait-and-check for deletion (lab 09 has one) and the verify does not look at the stack; if the owner skipped c-extra, deleting the stack makes any replica a promoted, running standalone instance (the cited page says so) that holds the DB subnet group, which leaves the stack DELETE_FAILED and the instance billing -> add a "wait until DELETE_COMPLETE; on DELETE_FAILED read the events and delete the named resource" step, and `aws cloudformation list-stacks --stack-status-filter DELETE_FAILED --query "StackSummaries[].StackName"` to v-db.
[medium] costs / steps stack, make-replica, restore, c-extra, c-stack: allocated storage (and provisioned IOPS if chosen) bills per GB while each instance exists, including the replica and the restored copy; `costs` only has compute and backups -> add an `rds-storage` cost with a page quote and list it on the same steps.
[medium] step make-replica: "Pick the smallest class offered" is ambiguous (the list is long and the replica may also be offered in another Region); nothing says single-AZ or same Region -> "db.t3.micro, same Region as the source, single-AZ" and add the cross-Region warning.
[medium] steps stack, snapshot, make-replica, restore: console detail pages show the stack ID or the DB/snapshot ARN with the account ID; none of these is `sensitive` -> set `sensitive: true`.
[medium] step v-db: `describe-db-instance-automated-backups` also lists automated backups of live databases (including the replica), so "must show nothing" is unclear while a database still exists; and it does not look at cross-Region copies -> use `--query "DBInstanceAutomatedBackups[?Status=='retained'].DBInstanceIdentifier"` for the retained check and say the check is only for your chosen Region.
[low] step deletion-policy: the quote proves the CloudFormation default is Snapshot; the claim that this template's `Delete` leaves no snapshot and no retained automated backups is the author's, not the page's (the cleanup `c-retained` is what actually protects the owner) -> add a quote from the DeletionPolicy page about `Delete`, or word it as "this template sets Delete".
[low] step stack: the template validates the password (12 to 40 letters and digits); the step only says "made-up password" -> say "12 to 40 letters and digits".
[low] template: `DBInstanceIdentifier: lab-10-rds` is fixed, so a second run or a failed delete blocks a new stack; `MultiAz` parameter allows `true` which doubles the cost -> drop the parameter (the lab never uses it) or keep and warn at the step (it does say keep false).
[low] bullets 2.2-S4 and 2.2-S1: no step practises failover or automation of integrity, only reading -> acceptable for the read-only path; either drop 2.2-S1 or add a sentence on automating the database with the template.
[low] step c-snaps: the final snapshot name depends on what the owner types in the delete dialog; the lab should say "tick no final snapshot" in c-extra and c-stack (c-extra does for the extras; c-stack is deletion by template so fine).
Checked and fine: replica-before-source order in c-extra; `BackupRetentionPeriod: 1` makes replicas possible; `StorageEncrypted` uses the default RDS key, so no customer managed KMS key exists; `PubliclyAccessible: false`, empty-ingress security group; retained backups and manual snapshots have their own cleanup and verify; no prices; plan badge "not confirmed" honest (RDS Free-plan fit is "rendered page" only; replicas and restores are not claimed free).

## Summary

Labs 06 to 10 are well structured and the order of steps works; no lab relies on resources deleted by an earlier lab's cleanup and the `needs` on lab-01 is cosmetic. The sharpest problems are in the paid-resource labs: lab 10's restore step does not constrain class or Multi-AZ and its cleanup has no stack-failure check (a promoted replica could remain billing), lab 9 omits EBS volumes and public IPv4 on the ALB from `costs` and cannot detect a DELETE_FAILED stack, lab 8 has a checkpoint (Scan uses more capacity) that will be false on a table this small and omits PITR from `costs`, lab 7 leaves Lambda log groups behind, and lab 6 does not warn about the wizard's WAF option and may duplicate the bucket policy the wizard writes. Several steps show ARNs (stack, table, snapshot) without `sensitive`. No prices, account IDs or emails were found; plan badges are honest ("not confirmed" for all five).

Counts (by severity): 2 high, 17 medium, 32 low (51 findings).
